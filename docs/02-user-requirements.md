**版:** v2.7 / **状態:** 要求ベースライン確定

## 2. 主要ユースケース

### UC-001: 日本語記事の要約

**前提:** 対応端末・ネットワーク・必要モデルが利用可能。  
**開始:** Chromeの共有メニューから本アプリを選択。  
**正常:** URL1件→HTTP取得→主本文抽出→日本語判定→日本語要約1〜3項目→SCR-004。  
**異常:** URL不正、非公開IP、HTTP失敗、抽出失敗、文字数不足、モデル未利用、推論失敗などはERRに分類。  
**終了:** 表示中のみ結果を保持し、キャンセル・離脱・新共有で破棄。

### UC-002: 英語記事の要約

UC-001の要約段階を英語要約→共通AIゲート再取得→日本語翻訳に変更。英語中間要約はセッションに閉じ、Firebaseへ送信しない。翻訳失敗時はERR-014。英語のまま結果を成功扱いしない。

### UC-003: モデル未取得

SCR-003で説明と明示同意を求め、Wi-Fi条件を満たす場合にモデル取得を開始。取得中に新共有が届けば旧記事はキャンセルするが、SDK管理のモデル取得は継続し得る。新記事が同じモデルを必要とする場合は取得状態を再利用し、重複ダウンロードしない。

### UC-004: 連続共有・再試行

別の共有操作はURL一致にかかわらず新SessionId。旧SessionIdの非同期結果、エラー、モデル準備完了通知は画面に反映しない。手動再試行は同一セッションに新ExecutionIdを付与し、URLの安全性確認から再実行する。キャッシュした本文やHTMLは使わない。

### UC-005: アプリ離脱

トップフォアグラウンドを実際に失った際、処理中・結果表示中のセッションを終了。復帰後はSCR-001。画面回転のような構成変更では重複実行せず状態を引き継ぐ。プロセス死からの起動ではURLや要約結果を復元せず、古いIntentを新しい共有と誤認しない設計を検証する。

## 3. Constraints（CON-001〜020）

| ID | 制約 |
|---|---|
| CON-001 | Android、Kotlin、Jetpack Composeを採用する |
| CON-002 | Chrome ACTION_SEND経由の単一HTTP(S)記事URLを処理する |
| CON-003 | 日本語・英語記事を対象とし、最終結果は日本語 |
| CON-004 | クラウドLLM・クラウド翻訳への送信・フォールバックを禁止する |
| CON-005 | 記事本文・AI入出力・要約履歴をアプリ独自に永続化しない |
| CON-006 | モデル取得は明示的承認・Wi-Fi条件に従う |
| CON-007 | 診断に使う記事URL情報は安全と判定したホスト名のみ |
| CON-008 | 危険なリダイレクト・ローカル/私設アドレスへの接続を禁止する |
| CON-009 | WebViewによるJSレンダリングやサイトログインをMVPに含めない |
| CON-010 | 新共有を優先し、旧実行結果を採用しない |
| CON-011 | 最前面喪失で記事セッションをキャンセルする |
| CON-012 | Firebaseへの明示的送信前に診断用URLを加工・検査する |
| CON-013 | 診断用ホストの安全性を確認できない場合は送信しない |
| CON-014 | ML Kit GenAI Summarizationを第一候補とするが正式採用はPoC/ADR後 |
| CON-015 | 手動DI・Single Activity・単一Gradle :appモジュール |
| CON-016 | Firebase Analytics・Performance・Crashlyticsを使用するが収集ポリシーを検証 |
| CON-017 | リリース前の実機検証をPixel 9 Pro XL一台に限定し他機種リスクを明示 |
| CON-018 | アプリ独自のSessionId・ExecutionId・相関IDをFirebase送信しない |
| CON-019 | GA4対象ユーザー・イベントデータ保持を2か月に設定する |
| CON-020 | Firebase SDKの自動収集にも禁止データ非送信を要求する |

| ID | 不変条件 |
|---|---|

| INV-002 | Compose再Compositionで新処理を開始しない |
| INV-003 | 画面回転によるActivity再生成で同一Intentを二重消費しない |
| INV-004 | プロセス死後、古いセッションを自動復元しない |
| INV-005 | 同時に有効な要約セッションは最大1つ |
| INV-006 | 旧セッションは新規共有受信時に直ちに無効化 |
| INV-007 | 旧セッションの非同期コールバックは新UIを変更できない |
| INV-008 | 旧モデル準備・旧エラーで新セッションの画面を出さない |
| INV-009 | 同じ処理・モデル取得を意図せず多重起動しない |

| INV-011 | 同一モデル構成のアプリ起点重複ダウンロードを抑止 |
| INV-012 | モデル準備状態は記事セッション終了で無条件消去しない |

| INV-018 | SDKの安全解放未確認なら実行権を次へ渡さない |
| INV-019 | 無効化したセッションのAI実行権待機は取り消す |
| INV-020 | モデルダウンロード待ちでAI実行権を占有しない |

## 5. 衝突解消ルール

- 「2メーカー以上の実機検証」とその後の「保有Pixel 9 Pro XLのみ」が併記された場合、**最後の明示的補足を採用**し、Pixel 1台を必須とする。他メーカーは未検証リスクを記録。
- 「内部テスト→一般公開」は**任意の**クローズドテストを省略する希望であり、Google Playが要求する必須クローズドテストを省略する許可ではない。
- 「新共有は即時受付」と「旧推論解放まで待機」は両立させる。待つのは**AI実行権**であり、共有イベントや画面切替ではない。
- 「キャンセル」は記事セッションの失効を意味し、OS/SDKが管理する進行中のモデルダウンロードの強制停止を意味しない。
- 「診断URLとしてホスト名のみ」はアプリによる明示的記録だけでなくFirebase自動計測へも適用する。検証不能なら自動計測を無効化する。
