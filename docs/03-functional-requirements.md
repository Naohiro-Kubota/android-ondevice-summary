# 03. 機能要件・エラー・機能Acceptance Criteria

**版:** v2.7 / **状態:** 要求ベースライン確定。PoC未完了の条件はゲート付。

## 適用ルール

- `FR-001〜062`を機能・実装責務の正本とする。すべてMUST。画面詳細は`05`、非機能制約は`04`。
- ユーザーに見せる失敗は`ERR-001〜017`。`ERR-010`（通常のモデル未取得）・`ERR-016`（キャンセル）・`ERR-017`（Firebase失敗）は通常の非致命的例外としてCrashlyticsへ記録しない。
- `AC-001〜167`は機能のGiven/When/Then。本文400文字以上を受け付ける要件を維持する。400文字ちょうどのSDK適合性とモデル解放方法はPoCで検証する。
- 既存の重複する記述（FR-013/038、FR-020/035）は矛盾ではなく、**振る舞い**と**UI要求**を分ける。

## 2. ERRレジストリ（全17件）

「再試行可」は**利用者の手動操作**であって自動再試行ではない。`ERR-015`の解放待ち上限値・BUSYとクォータの詳細分類はTV-007/008で確定。

| ID | 状況 | 手動再試行 | 案内・対応 |
| --- | --- | --- | --- |
| ERR-001 | 共有URLの欠落・複数・形式不正 | 不可 | 共有元からURLを1件のみ共有 |
| ERR-002 | 危険なURL・禁止接続先 | 不可 | 公開記事URLを確認 |
| ERR-003 | HTTP取得失敗 | 接続失敗/429/5xxのみ可 | 接続状態や公開状況を確認 |
| ERR-004 | 時間切れ・レスポンス過大 | 時間切れのみ可 | 時間を置く／大きすぎる記事は対象外 |
| ERR-005 | 危険なリダイレクト | 不可 | 転送先が安全な記事を共有 |
| ERR-006 | 主本文の抽出失敗 | 不可 | 本文を取得可能な記事を共有 |
| ERR-007 | 本文が400文字未満 | 不可 | 十分な本文のある記事を共有 |
| ERR-008 | 言語非対応・判定不確実 | 不可 | 日本語か英語の記事を共有 |
| ERR-009 | 端末で要約機能が利用不可 | 不可 | 対応機能・端末を確認 |
| ERR-010 | モデル未取得・準備承認待ち | SCR-003へ | Wi-Fi接続後に承認（通常状態として診断） |
| ERR-011 | モデルダウンロード失敗 | 条件付き可 | Wi-Fiと空き容量・状態を確認 |
| ERR-012 | 調整後もAI入力が長すぎる | 不可 | 別の記事を共有 |
| ERR-013 | 要約推論失敗 | 原因が一時的なら可 | 状況を確認して手動再試行 |
| ERR-014 | 日本語翻訳失敗 | 原因が一時的なら可 | 状況を確認して手動再試行 |
| ERR-015 | AI BUSY・資源待機上限・クォータ | BUSY/一時失敗のみ可、クォータ上限は不可 | AIの状態に応じて案内 |
| ERR-016 | 利用者キャンセル | 対象外 | エラー画面に遷移しない |
| ERR-017 | Firebase診断失敗 | 対象外 | 要約処理に影響を与えない |

## 4. 主な業務規則

- **FR-053とFR-049は別:** 同じURLの再共有は別共有イベントなら新セッション。画面回転による古いIntentの再評価は新共有ではない。
- **FR-055とFR-047は別:** 旧推論が止まるまで待つのはAI実行権のみ。新共有受付と旧Session失効は直ちに実施。
- **FR-056/057:** モデルダウンロード状態の再利用で記事本文・URLの共有や復活を起こさない。
- **FR-020/035:** SDKが百分率を返さない状態で偽の進捗を作らない。
- **ERR-015:** 資源待機上限超過は現在の候補ERR-015に割当。実機PoCとADR-004の承認で文言・詳細カテゴリを確定。
- **FR-027とAC-031/032:** 日本語公式ドキュメントが「400文字以上」、英語公式ドキュメントが「400文字を超える」と表記する差があるため、**本アプリ要求は400文字以上を受理する**。TV-003でSDKの受理挙動を検証し、SDKが要件を満たせなければPoC不合格・代替方式/人間の判断とする（要件を無断変更しない）。

## 5. エラーと画面の関係

- ERR-001〜009、011〜015は原則SCR-005に公開コード・理由・対処・再試行条件を表示。
- ERR-010は通常SCR-003のモデル準備を案内する状態であり、Crashlytics例外ではない。
- ERR-016は取消イベント。SCR-001に戻り、エラー画面へ進まない。
- ERR-017は診断内部の失敗。記事処理を失敗にしない・再帰的に記録しない。

## 6. 開発・承認の関係

FRのMUSTを変更する際は、GitHub Issue・ADRまたは要件差分と人間の承認を伴う。PoC不合格はFRを黙って省く理由にならない。
